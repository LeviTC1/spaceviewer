# Planetary rendering and texture integrity

Solar Explorer separates orbital state from appearance. VSOP87/Keplerian providers determine the object position; the material layer consumes local image assets and clearly identifies its shaders and presets as visual approximations.

Body attitude is separate again: the Sun and planets use the date-anchored IAU/IERS orientation provider documented in [planetary-body-orientation.md](planetary-body-orientation.md). The bundled textures have no verified cartographic seam or longitude-origin metadata, so a scientifically defined body frame does not imply surveyed landmark-to-meridian registration.

## Texture provenance and inventory

The repository contains 34 files under `frontend/public/solar-textures`: 17 high-tier and 17 performance-tier assets. The v2 source inventory resolves every public file through a verified upstream receipt, a controlled local-generation receipt, or a declared derivative of one of those assets.

- Ten high-tier maps are byte-identical to Solar System Scope downloads. Its official texture page applies CC BY 4.0 and permits adaptation and commercial reuse with attribution.
- Earth atmosphere, cloud, night-light and specular maps plus the Moon map are byte-identical to pinned historical three.js files under the repository's MIT notice.
- Pluto now uses NASA's New Horizons global colour mosaic rather than the former fictional pre-flyby rendering. The catalog source preserves the exact downloaded bytes, NASA/JHUAPL/SwRI credit and NASA media-usage conditions; the public copies are controlled browser-sized derivatives.
- The gas-giant detail noise is emitted locally from a fixed xorshift32 seed and contains no third-party image.
- Performance-tier maps are regenerated by the recorded ImageMagick 7.1.2-18 Lanczos recipe. Each output hash and `derivedFrom` relationship is part of the manifest.

From `frontend`:

```bash
npm run textures:fetch
npm run textures:fetch:check
npm run textures:audit:sources
npm run textures:derive
npm run textures:build
npm run textures:check
```

The fetch command hash-locks the NASA source; the source audit re-downloads all 15 direct upstream assets and proves byte identity. The derivative command rebuilds Pluto, both quality tiers and deterministic noise from the recorded recipes. The manifest builder reads PNG/JPEG dimensions, byte sizes and SHA-256 hashes, rejects unreceipted files, validates the pinned NASA source file and writes `public/solar-textures/manifest.json`. It also records duplicate files across quality tiers and flags both `earth_atmos_2048.jpg` copies as unreferenced by the runtime.

The UI links both the machine-readable manifest and `ATTRIBUTION.txt`. The receipts remove the former unknown-origin blocker, but remain an engineering provenance record rather than legal advice. Redistribution must retain the attribution/notice file, follow CC BY 4.0, MIT and NASA media-usage conditions, and avoid implying endorsement.

## Material path

- Surface colour textures use lit planet materials. Earth retains its local specular mask instead of incorrectly treating that mask as a roughness map.
- Earth clouds and night emission rotate and illuminate independently from the base surface.
- Sun and planet surfaces consume one deterministic body-fixed frame derived from the simulation date; pausing freezes the frame and reverse time retraces it. Cloud/noise drift remains a separately disclosed presentation layer.
- Earth and Mars atmosphere shells use a cached, quality-sized single-scattering optical-depth LUT with spherical density integration, RGB Rayleigh ratios and the real scene Sun direction. Earth consumes the published Bruneton reference parameterization; Mars is explicitly a JPL-density-scaled provisional molecular profile with no invented dust coefficient.
- Venus and the giant planets retain the compact sun-aware analytic limb fallback and identify that boundary in their dossiers; the terrestrial table is not silently reused for unlike atmospheres.
- Mercury and Pluto no longer receive a substantial generic atmosphere shell.
- Saturn's one-dimensional ring strip is sampled radially rather than stretched over Cartesian UVs.
- Saturn and Uranus now use source-carrying physical radial systems. Ring fragments run a finite-Sun analytic ray/sphere test, while a separate ring-plane transmission pass projects the rings onto the illuminated planet without fake painted bands.
- Selected planets receive finite-solar-disc major-moon shadows from physical radii and scientific-unit vectors. Exact apparent-disc overlap produces continuous umbra, antumbra and penumbra intensity. Earth's Moon and the Galilean moons use controlled analytical states; other moon systems retain illustrative seed timing.
- Gas-giant noise is explicitly identified as an artistic detail overlay.

The UI surfaces the active map roles and visual-approximation status for Sun, planets and textured moons, with direct links to the generated manifest and attribution notice.

## Runtime texture streaming

Solar Explorer no longer treats the complete texture inventory as a boot dependency. `preloadSolarEssentialTextures()` waits only for the Sun assets already required by the mounted solar presentation. Asteroid assets retain their separate layer-owned request path.

Every planet renders immediately from its recorded colour hint. The surface texture request begins when the planet is selected, hovered or enters the near LOD threshold; far and mid-distance planets do not fetch their maps merely because their meshes are mounted. A selected body can therefore promote from the fallback to the appropriate performance/high map without blocking the initial canvas.

Moon meshes are already parent-visibility gated. Their shared surface map is requested only after the relevant planetary system is close or selected, not for every major moon during startup.

The shared texture cache deduplicates both pending promises and completed assets. Pure tests cover the promotion policy. Browser smoke verifies on-demand Mars and Europa requests, and isolated cold-load checks fail when the overview requests more than three planet surface maps. High-tier assets remain absent from Balanced/Low boot.

## Scientifically honest scale models

Solar Explorer now exposes three explicit heliocentric spacing contracts:

- **Cinematic** uses the existing logarithmic AU compression for a compact dramatic atlas.
- **Educational** uses square-root AU compression to open the outer system while retaining one readable overview.
- **True AU** maps one astronomical unit to exactly 30 scene units. Heliocentric distance ratios are linear: an object at 10 AU is rendered ten times farther from the Sun than an object at 1 AU.

The True AU label is deliberately narrower than “true scale.” Planet, moon and Sun radii remain exaggerated and the moon projection retains a minimum parent-clearance distance so those bodies stay selectable. The legend, Mission panel and direct route all disclose that boundary; SpaceViewer does not imply that rendered body diameter and orbital distance share one physical ruler.

Each scale has a dedicated camera/fog/light envelope. True AU extends the camera to 3,200 scene units, the far plane to 8,000 and the overview far enough to retain the outer-planet context. Its non-decaying point light is a separately tuned presentation control that preserves surface-texture colour at close range; it is not a physical irradiance calculation. Direct URLs and saved camera bookmarks preserve the scale, for example `/solar?object=overview&mode=ecliptic&scale=realistic`. Planet focus distance is now based on visible body radius rather than heliocentric orbit radius, preventing outer-planet fly-to from stopping hundreds of scene units away.

Close focus also normalizes a nearly polar incoming camera vector to a stable oblique direction, so a top-down system view does not turn the next planet fly-to into an accidental polar-only inspection. Planet, moon and selected-orbit HTML labels use screen-stable sizing at close range instead of scaling across the viewport with camera distance.

Pure regression tests cover linear AU ratios, the distinct compressed mappings, the outer-system camera envelope, radius-based focus distance, bookmark persistence and URL round-tripping.

## Solar navigation and share contract

Every Solar target is serialized as one canonical route containing an object selector plus the active camera mode, spacing model and UTC date. Planet, moon, Sun and belt selections push a browser-history entry; date, camera and spacing refinements replace that entry. Search, tour, event-preset and bookmark actions assemble their final context before emitting the route, avoiding intermediate history noise.

Back/Forward applies the target to the existing React and WebGL scene rather than navigating through a renderer remount. Returning to plain `/solar` clears the selection to the explicit system overview. Mission Control's copy-link button canonicalizes the current state, copies the absolute URL and exposes accessible copied or failed feedback. Exact free-orbit camera pose is not serialized yet; the route restores the declared camera mode and focused object.

Unit tests cover the snapshot-to-route priority and context round trip. Desktop smoke coverage selects Mars and Europa at 1280×720, checks Back/Forward, date and True AU restoration, compares WebGL lifecycle counters, exercises copy-link feedback, and confirms that Back from a newly selected Saturn to plain `/solar` clears the details view.

## Production continuation

1. Add reviewed normal/height/roughness inputs only where their channel semantics are known.
2. Extend the generated Earth/Mars single-scattering path with reviewed body-specific spectral, absorption, aerosol and multiple-scattering inputs; keep the analytic fallback where no controlled profile exists.
3. Extend the controlled Moon/Galilean path to other major satellites where a receipted source and test oracle are available; add satellite attitude/shape and light-time inputs before making predictive timing or ground-track claims. Then extend ring transmission with oblateness, measured wavelength-dependent profiles and vertical structure where the visual return justifies it.
4. Replace browser-time and generic text-PCK orientation approximations with controlled binary SPICE PCK/CK, explicit time-scale conversion, Earth-orientation inputs and the high-accuracy NAIF lunar frame path where their precision is justified.
5. Capture headed, hardware-accelerated GPU traces before claiming the desktop frame-rate target.
